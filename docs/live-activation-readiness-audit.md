## 3. Authentication / Account Identity

**P2 MONITOR** for latency; **P1 BEFORE LAUNCH** for account onboarding. [Login](../lwrpc-admin/app/login/page.js) calls `signInWithPassword`, then `auth.getUser`, looks up members by email with embedded `user_roles`, obtains the session, makes one `/api/account-identity` POST (browser timeout six seconds), and routes by highest active-member role. [Account identity](../lwrpc-admin/app/lib/accountIdentity.js) revalidates the token server-side and calls the `link_future_existing_member_identity` RPC with a three-second deadline. Its 503 `retry_later` means RPC error, `BUSY`, timeout, or a caught server-side exception; it is intentionally non-blocking to login. The underlying [prospective-link function](../lwrpc-admin/supabase/migrations/20260907143225_lms0723_identity_coordination.sql) uses scoped advisory/row `NOWAIT` locks and returns `BUSY` on lock contention. A failed authentication branch in this specific route maps to 401, not 503.

Once routed, [Captain Dashboard](../lwrpc-admin/app/captain-dashboard/page.js) performs its own session/member/role check and member lookup, then sequential divisions, club-pro locations, assigned teams, published matches, published division-match summary, roster/standings in parallel, ratings, match-setup state, and byes. A separate Weekday document lookup runs on mount. This is roughly ten-plus Data API reads after authentication when a captain has a team; it is a latency waterfall, but most reads are scoped to assigned teams/divisions. The `useEffect` loaders run once per Production mount absent remount/dependency changes; React development-mode effect duplication is not evidence of duplicate Production traffic. There is no evidence of a per-player query loop on initial dashboard load. Deep match/line/member embedding may become the first post-publication latency hotspot, especially for captains with multiple teams. The dashboard's visible minimum-load timer is not a DB bottleneck.

Current-deployment runtime logs show one `POST /api/account-identity` 503 at 2026-09-22 21:01 UTC, versus 488 HTTP 200, 46 HTTP 304, six `/_not-found` 404 and one 503 in the current-deployment 24-hour result set. No repeat account-identity 503 appears in that set. The log has a route/status but no RPC outcome, elapsed phase, response body, or request correlation, so **the exact cause cannot be distinguished** among `BUSY`, database/RPC error, the three-second RPC deadline, missing server configuration, or a platform-level response. An expected 78-member update occurred around 21:00 UTC, but temporal proximity is not proof of contention. Do not label this an Auth saturation event. If two or more account-identity 503s or login complaints recur in a short window, inspect correlated Supabase Auth/RPC and Vercel logs before changing the endpoint.

For onboarding, the [existing Forgot Password/account-setup handler](../lwrpc-admin/app/api/member-password-reset-check/route.js) can invite an active member with no Auth account when email delivery is active; current `email_activated` setting is true. It calls Supabase Auth admin list-users and invite/recovery services; do not mass-trigger this handler merely as a test. Of the 104 distinct assigned primary captains on active teams, 18 active members have no matching Auth email account. Login cannot work for them until normal invitation/setup is completed. The existence of an unlinked `user_roles.user_id` alone is not the same as absence of an account, because login resolves role by member email.

## 7. Master Schedule Generation

**P1 BEFORE LAUNCH** for all-team coverage/operating procedure; **P2 MONITOR** for current Fall compute size. [Scheduling](../lwrpc-admin/app/scheduling/page.js) is a client component. It first reads leagues, divisions, locations, teams, special requests, settings, court availability, blackouts, and **all** matches into the browser; special requests are documented informational-only and are not enforced by the generator. Each Generate action is **division-setting scoped**, not one league-wide server job: it fetches that division's active teams, builds a round robin in JavaScript, adjusts for blackouts/every-other-week/byes, checks home/away court availability against existing and planned matches, and writes one batch of matches, then byes, then match lines, then line games. This work does **not** execute inside one Vercel Function, so the 300-second function duration does not protect or limit it. Browser lifetime/network and Supabase HTTP/query limits matter instead.

At the 2026-09-22 team counts, 12 settings cover 103 active teams and project to approximately **347 matches, 4,423 match lines, 4,703 line games** across 12 separate Generate actions (arithmetic from current team counts, weeks, and division-line templates; not a live generation or elapsed-time measurement). The nine Fall settings project to 259 matches/2,191 lines/2,471 games. The largest *Fall* setting has 15 teams, seven weeks, about 49 matches and 441 line rows. This is modest browser-side planning, but end-to-end seconds/minutes cannot be certified without an isolated representative rehearsal. Saturday `SDUPR7` currently projects 40 matches and **exactly 1,000** returned match-line rows in one `.insert(...).select()`; any increase or a lower configured Data API result cap would risk incomplete returned IDs and therefore missing game creation. Confirm actual Max rows and a staging rehearsal before that largest Saturday run.

The current multi-request write sequence is **not atomic** across matches, byes, lines, and games. A failed bye/line/game call can leave earlier rows committed; the helper alerts and returns, while the outer flow may still report generated matches. Re-clicking after partial failure can create duplicates because the existing-match warning is confirmable, not an idempotency guard. Court conflict checks use a browser snapshot, so two operators generating concurrently could race; single Commissioner operation is the safe procedure. Before each division: verify settings, location/court/blackout data and no existing partial schedule; generate once in a quiet, supervised window; then reconcile expected match, bye, line, and game counts and inspect warnings before proceeding to the next division or publishing. Do not automatically delete/retry; use the protected recovery process and obtain owner authorization for any business-data correction. Low traffic is prudent for operator focus and DB headroom, not because the current planner appears CPU-heavy.

Three active PrimeTime divisions have no saved setting: `MPT 7` (two teams), `WPT 7` (four), `WPT 9` (four). They cannot be included in an all-team run through the current setting list. Confirm whether they are intentionally scheduled manually; if not, prepare settings through the normal authorized workflow before master-schedule week. No settings or schedules were changed here.
